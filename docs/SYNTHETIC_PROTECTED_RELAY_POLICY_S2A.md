## Source-only policy contract

`src/synthetic-protected-relay-policy-s2a.ts` defines a **pure policy planner**:

- **Caller request:** one 1.3 `SyntheticSyncOffer`, expected remote revision ID or null, and an exact versioned resource scope: `tenantId`, `clientId`, `engagementId`, `sessionId`. It carries NO credentials, client names, answers, private notes, or server claims of authentication. Reject additional fields, incompatible schemas, invalid IDs and a forged operation ID. Validate the deterministic S1 operation ID against the exact offered head.
- **Future server-sourced gate (SYNTHETIC ONLY):** named actor, exact same four-part resource scope, active actor and assignment, and explicit `append` privilege. A marker reading `server-policy-test-fixture` is **NOT trusted evidence**. This policy object can be fabricated by any caller; until a real protected backend independently authenticates actor identity and reads up-to-date enrollment/grants from its authoritative private store, the planner's `candidate-append` outcome MUST NOT authorize anything. A browser must never supply this gate.
- **Future server-sourced stored state (SYNTHETIC ONLY):** same exact scope, current authoritative revision head or null, and one *already durably stored* exact scoped receipt or null. A browser-provided object cannot establish this state. Unreadable, invalid, cross-engagement, cross-session or 1.4 state fails closed.
- **Four output kinds:** `deny` (generic, **no object IDs or remote state**); `candidate-append` (expected remote revision and offered next head); `candidate-conflict-preserve` (only after the supplied scope/grant passes, both heads for human review, never overwrite); `candidate-replay` (only if the supplied stored receipt exactly matches resource, operation ID, revision and snapshot digest). No output is a legitimate remotely committed `SYNCED` indication, signed receipt, confidentiality guarantee, or authority grant.
- **CAS rules:** for a new session, expected remote is null and offered parent is null; for an existing session, the offered immediate parent AND expected remote must match the current revision, with matching pack identity and a distinct next revision. Same-ID digest discrepancy, unknown ancestry, stale expectations and offline sibling edits **preserve conflict**. No last-write-wins/CRDT answer merge or automated client statement acceptance.
- **Retry rules:** reusing an operation ID is *not* proof of an earlier durable write. The planner requires a matching previously stored receipt to return `candidate-replay`; otherwise treat the state as an unresolved conflict or fresh CAS proposal. The operation hash itself is deterministic metadata, **not** an authenticator or replay-defense secret.

Pure Vitest cases cover first insert, correct single-parent advance, two offline siblings, race preconditions, tenant/client/engagement/session substitution, revoked actor and assignment, missing action, forged/malformed operation IDs, unrelated receipts, 1.4, unknown fields, missing/hostile stored state and no private output leakage. No external data, network, secrets, provider, persistence, package or app entry path is involved.

## Production threat model / mandatory future server duties

**Before S2B**, the owner/security/ClientOps must separately approve all of the following (no automatic selection from this document):

1. **Identity and object-level authorization.** Every read/append/receipt/status request must authenticate the actor through a trusted provider session or equivalent, resolve current actor-to-tenant/client/engagement/session authorization from *server-owned* sources, and recheck active grant/revocation on each request. Never trust client-submitted actor/grant/tenant assignment or a forged `source` marker. Do not cache grants indefinitely. Deny by default; avoid disclosing cross-client IDs, conflicts or revision metadata on denial. Separate read permissions must be designed/tested, not inferred from append permission. Follow [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).
2. **Atomic server-side CAS + scoped idempotency.** Use an atomic provider transaction/conditional update spanning current authoritative revision, retained immutable revision, scoped operation ID and durable stored receipt. Concurrent requests that planned against one parent must not both commit. Do **not** accept the pure planner result alone as a commit. Require conditional write against the exact current remote revision (strong HTTP `If-Match`/ETag semantics are one candidate, [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)); map stale writes to an authenticated conflict response, preserve both branches, never return a false success.
3. **Verified session content + storage.** A future protected adapter must independently validate canonical uploaded 1.3 session bytes and SHA-256 snapshot digest, pack/schema and expected parent, size bounds, allowed MIME, tenant retention, non-public logs, object-level data access, quotas and full revision lineage. The S2A planner receives only metadata and cannot prove the body was delivered or durably persisted.
4. **Transport confidentiality and truthful ACK.** Enforce TLS, robust server authentication, CSRF/origin/replay controls where applicable, secure secret management, per-engagement storage isolation, audited permission/deletion, retention and access revocation. A response counts as remote `SYNCED` only after verified authenticated durable commit and local exact operation+scope receipt persistence. Treat outage, auth failures and corrupted responses as **QUEUED/ERROR**, retaining data safely; no background sync assumptions.
5. **Confidential recovery and release.** S2B private synthetic host requires verified $0 entitlement and approved data classification/retention; #35 encrypted off-device key-custody/recovery/physical-device acceptance; #105 ClientOps engagement identity/protected owner launch; owner-controlled pilot approval. A sync service is not a complete encrypted backup. Do not put any real client content, metadata, tokens or persistent private URLs into GitHub, source tests, logs, public analytics, service worker app cache or Owner Console status.
